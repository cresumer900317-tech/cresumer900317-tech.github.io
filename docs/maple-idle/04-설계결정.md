# 데미지 계산기 — 설계 결정 기록

2026-08-07 논의분. **왜 그렇게 정했는지**가 핵심이다. 이 문서 없이 작업하면 같은 논의를 처음부터 반복하게 된다.

## 0. 만들려는 것

**"현재 내 스탯에서 뭘 올리면 더 세지나"** — 스탯/잠재 옵션 효율 랭킹이 본체.
아이템 A vs B 비교는 그 응용.

절대 DPS는 **부가 기능**. 클리어 시간 예측·공속/쿨감 평가에만 필요.

대상: 친구패밀리 길드 100명. 배포는 웹(친구들.com) + 앱 WebView.

## 1. 핵심 아키텍처 — AI에게 계산을 시키지 않는다

기존 `item-compare` 구현의 정확도가 낮았던 근본 원인.

```
[1] 파싱   AI 비전: 스크린샷 → {옵션명, 수치} JSON      ← AI가 잘하는 일
[2] 계산   결정론적 수식 (JS)                          ← LLM 완전 배제
[3] 설명   계산 결과를 문장으로                          ← 템플릿으로 충분
```

기존 백엔드(`guild_backend/item_compare.py`)는 `_OUTPUT_SCHEMA.verdict`(winner/by_content/reason)를
**모델이 생성**한다. 20단계 곱셈 체인을 자연어 추론으로 근사하는 구조라 맞을 수가 없다.

### 조치
- `verdict` 스키마 제거 → 파싱 전용으로 축소
- 판정이 빠지면 Opus 5 + effort medium이 과잉 → **Haiku로 다운그레이드** (비용·지연 대폭 감소)
- 프롬프트의 "실전 가치 통설" 블록(127~131행) **삭제**
  - "★ 기본 공격 데미지가 이 게임 최고 가치 옵션" = 근거 없는 통설. 개인차를 무시한다
  - 휴리스틱은 계산이 없을 때의 대용품. 계산이 생기면 걷어낸다

## 2. 정확도가 낮았던 진짜 원인 — 입력 결핍

프로필로 받던 6개(직업·레벨·크확·콘텐츠·딜스타일·메모)로는 **원리적으로 계산이 불가능**하다.

합산 스탯의 한계효용은 **현재 보유량에 반비례**한다.

| 내 현재 데미지 | "데미지 +10%" 옵션의 실제 값어치 |
|---|---|
| 50% | +6.67% |
| 200% | +3.33% |
| 500% | +1.67% |

같은 옵션이 사람에 따라 4배 차이. **현재 스탯 없이는 어떤 AI를 붙여도 못 맞힌다.**

## 3. 입력 방식 — 스탯창은 손입력

**스크린샷 파싱을 스탯창에 쓰지 않기로 결정.** 이유:
- 스탯창이 스크롤이라 한 화면에 안 들어감 → 여러 장 이어붙이면 누락·중복 판정이 새 문제로 들어옴
- 스탯창은 **보유한 옵션만 뜨는 동적 목록** → 사람마다 줄 수가 다름
- 손입력이 더 정확하고 저렴

### 파서 설계 원칙 (아이템 팝업용)
- **라벨 매칭 + 없으면 0**. 항목 위치 고정 가정 금지
- 등록 후 새 옵션이 생기면 항목이 늘어남 → 재등록 유도 필요

### 스크린샷이 살아남는 자리
```
스탯창 (스크롤, 40행)     → 손입력, 1회, localStorage
아이템·잠재 팝업 (1화면)   → 캡쳐  ← 기존 /api/item-compare/analyze 재활용
```

### 입력 항목: 40개 중 21개만
**필수(21)** 직업·레벨·공격력·주스탯·부스탯·스탯비례데미지·데미지·데미지증폭·최종데미지·
기본공격데미지·스킬데미지·보스몬스터데미지·일반몬스터데미지·상태이상데미지·방어관통력·
크리티컬확률·크리티컬데미지·최소데미지배율·최대데미지배율·명중·공격속도

**선택(8)** 쿨감%·쿨감(초)·기본공격대상수·버프지속·동료소환지속·1~4차/모든스킬레벨

**안 받음(11)** 전투력·방어력·최대HP·최대MP·초당MP회복·받는피해감소·회피·디버프내성·
경험치획득량·메소획득량 — PVE 딜에 안 들어감. PVP 탭 만들 때만 추가

### 입력 UX
- **게임 스탯창 순서 그대로** 배치 (순서가 어긋나면 제일 헷갈림)
- `inputmode="numeric"` + 엔터로 다음 칸 자동 이동
- localStorage 저장, 스펙업 때 바뀐 칸만 수정
- 입력하는 동안 결과가 실시간으로 차오르게

## 4. 미지수를 없앤 방법

| 문제 | 해결 |
|---|---|
| 대상 방어력 (게임에 표시 안 됨) | **mgf.gg 스테이지 데이터 356개** → `03-스테이지-몬스터.json` |
| 스킬 계수 · 타수 · 사이클 | 옵션 비교에서 **약분**. 절대 DPS는 **클리어 시간 역산** |
| 스킬 마스터리 700개 | 약분 + **딜 비중 하나로 흡수** |
| 모든 스킬 레벨 파급효과 | 계산 불가 → **길드원 before/after 스탯창 제출** |
| 직업별 버프 효과 | **버프 ON/OFF 스탯창 2장** (버프는 껐다 켰다 자유) |
| 육각 수정 목걸이 곱연산 | **유물 체크박스** |
| 유효스탯 → 공격력 전환계수 | 장비 뺐다 꼈다 하며 공격력 변화 관측 (1분) |

### 절대 DPS 역산 캘리브레이션
```
실효 DPS = 몬스터 HP ÷ 클리어 소요 시간
```
이 상수 하나가 스킬계수·타수·사이클·마스터리 피해증가를 **전부 흡수**한다.
직업 14개 × 스킬 전부를 실측하는 작업이 **스톱워치 한 번**으로 대체된다.

한계: 공속·쿨감은 사이클 자체를 바꾸므로 상수가 흔들림 → 근사.
검증법 = 공속 옵션 바꾸고 같은 스테이지 다시 재기.

## 5. 수집 정책 — 무엇을 DB로 만들고 무엇을 입력받나

```
게임에서 볼 수 있고 + 사람마다 다르고 + 패치마다 바뀐다  →  DB 만들지 말고 입력받기
고정이고 + 모두 공통이고 + 잘 안 바뀐다                 →  DB로 내장
```

| DB로 내장 (≈300행) | 사용자 입력 |
|---|---|
| 몬스터 방어/회피/HP (356행) ✅확보 | 캐릭터 스탯 21칸 |
| 마스터리 습득 레벨 (51개) ✅확보 | **스킬 계수** (레벨 종속) |
| 직업↔주/부스탯 (14행) ✅확보 | **마스터리 수치** (레벨 종속 여부 미확인) |
| 스킬 목록·기본쿨·효과종류·지속시간 | 버프 효과 수치 |
| 마스터리(쿨감·버프강화·스킬피해량) | 보유 유물 |

**스킬 계수는 레벨별 테이블을 만들면 안 된다.** 게임이 현재 레벨 기준 계수를 이미 보여준다
(블래스트 460.5%처럼). 각자 자기 걸 보고 한 칸 채우면 끝. 밸런스 패치에도 안 썩는다.

**쿨타임은 스킬 레벨 무관** → DB 가능. (확인됨)

**마스터리 중 안 모으는 것**
- 전역 스탯 (스킬데미지 +15% 등) → **이미 스탯창에 포함. 넣으면 이중 계산**
- 이게 마스터리를 수집할 때 제일 흔한 오류

## 6. 계산 규칙 (사전에서 확정)

### 천분율
표시 30% = 계산상 300. `(1+데미지) = (1,000+수치) ÷ 1,000`

### 누적 방식
| 방식 | 대상 |
|---|---|
| 기본 합산 | 데미지류 대부분 |
| **효과별 곱연산** | **최종 데미지만** |
| 체감 누적 | 받피감·방관·쿨감%·공속 — `1-(1-a)(1-b)…` 구조, 캡 기준으로 |
| 합 + 배율 | 공격력·방어력·최대HP/MP·주스탯 → **고정값 합산 후 % 배율** |

### 검증된 공식 ✅
```
유효 스탯 = 주스탯 + 부스탯 ÷ 4          (공격력·스탯비례뎀 양쪽 다 4:1)
스탯 비례 데미지(천분율) = 유효 스탯 × 0.1

실측: STR 107,109 + DEX 1,635/4 = 107,517.75 → 1075.18%
      게임 표시 1075.1%  ✅ 소수점까지 일치
```

### 방어력
```
배율 = 5,000 ÷ (관통 후 방어력 + 6,000)
관통 후 방어력 = 대상 방어력 × (1,000 − 방관) ÷ 1,000
```
최종 챕터 방어 7,100 기준: 방관 0%→0.382 / 50%→0.524(+37%) / 100%→0.833(+118%)

### 콘텐츠 압축 — 반드시 별도 표시
| 콘텐츠 | 보정 | 딜 2배 → 클리어 시간 |
|---|---|---|
| 사냥 | 없음 | −50% |
| 보스·길드레이드·파퀘 | **제곱근** | **−29%** |
| 길드 수련장 | **세제곱근** | −21% |
| 아레나·콜로세움·월드아레나 | 제곱근 + 레벨보정 + PVP방어보정 | 별개 |

"장비 갈아끼웠는데 보스에서 체감이 없다"의 원인. 압축 전/후를 나눠 보여줄 것.

### PVP (나중에)
방어 보정 분모 지수: **받피감 ^0.5** ≫ 공격종합 ^0.23 > 방어 ^0.14 > 최대HP ^0.12
- 받피감이 압도적
- **피격자의 공격 스탯도 분모에 들어감** → PVP에선 공격 스탯이 방어 역할도 함

## 7. 육각 수정 목걸이 — 특수 취급

사전 2번에 **이름째로 명시된 유일한 예외**.
> 데미지 **기본 수치**에 별도로 곱연산. 전투 중 스킬로 더해진 데미지에는 곱해지지 않음. 최대 3중첩.

- **항상 3중첩 유지**됨. 버프 지속시간과 무관 (확인됨)
- 실측 배율: 841.8% → 1567.9% = **×1.863**
- 육각 하나가 딜을 **1.77배**로 만든다 → "거의 모든 콘텐츠 필수"가 사실
- 상시 옵션(잠재·장비)은 기본 수치에 합산되므로 **육각 배율을 그대로 받는다**
  → 데미지% 옵션의 실효가 1.863배

**교훈: 유물 특수효과는 일반 공식으로 못 잡는다. 보유 유물 체크박스 필수.**

## 8. 옵션 분류 — 적용 범위로 갈린다

| 범위 | 옵션 |
|---|---|
| **전체 딜에 곱해짐** | 공격력·주스탯·스탯비례뎀·데미지·데미지증폭·**최종데미지**·방관·크리·최소/최대배율·보스/일반몹뎀·**받는피해증가(디버프)** |
| **평타에만** | 기본공격 데미지 · 기본공격 대상 수 |
| **스킬에만** | 스킬 데미지 · 쿨감 |
| **측정해야 앎** | 모든 스킬 레벨 |
| **조건부** | 상태이상 데미지 · 버프 효과(가동률) |

→ **딜 비중(평타 : 스킬)이 필수 파라미터.** 없으면 기본공격뎀·스킬뎀·쿨감·대상수를 평가 못 함.
얻는 법: ① 슬라이더 감 입력 ② 역산 측정 ③ 스킬계수+쿨+타수로 계산

## 9. 전투력 함정 — 이 도구의 존재 이유

전투력 가중치가 실전 기여와 어긋나는 항목들.

| 옵션 | 전투력 가중치 | 실제 딜 |
|---|---|---|
| **기본 공격 대상 수** | **×30,000** (1위) | **보스 0%** / 사냥 최상급 |
| 모든 스킬 레벨 | ×6,000 | 측정 필요 |
| **명중** | ×4,500 | 몬스터 회피 넘으면 **0%** |
| 최대 MP | (MP−500)×10 | **0%** |
| 방어 관통력 | ×1,000 | 큼 |
| 최종 데미지 | ×700 | 큼 |

기본공격 대상 수 +1 = 전투력 +3% (최종데미지 +4.3%와 맞먹음). 보스전 딜은 0.

**마스터리를 전부 습득하면 전투력이 약 10배**가 된다 → 전투력 숫자의 대부분이 마스터리에서 나옴.
전투력으로 아이템을 판단하면 안 되는 이유.

**출력에 `전투력 Δ` vs `실제 딜 Δ`를 나란히 표시할 것.**

## 10. mgf.gg와의 관계

mgf.gg에 **이미 데미지 계산기가 있다** (`/calc/calc.php`).
스테이지 선택·Δ 시뮬레이션·옵션 가치 순위·타수/공격주기·프리셋·공유링크까지 있고,
계산식은 `damage_calc_api.php`로 서버에 숨겨져 있다. 넥슨 공식 가이드가 2026-08-06 공개됐으니
mgf 계산기는 **역산 추정 기반**일 가능성이 높다.

### 남는 차별점
1. **잠재옵션 특화** — "지금 뜬 후보 중 뭘 고를까". mgf는 범용 Δ 시뮬레이터
2. **후보 팝업 캡쳐 → 순위** — 옵션을 손으로 안 옮겨적음
3. **직업별 버프 가동률 판정** — mgf는 직업별 버프를 모델링하지 않음. 100명 데이터가 있어야 가능
4. **함정 경고** — "가동률 이미 100%, 가치 0" 같은 판정
5. 길드 통합 · 공식 문서 그대로

**잠재는 되돌릴 수 없으니** 사전 판단의 값어치가 아이템보다 훨씬 크다. 이게 1번의 근거.

### 데이터 사용
`stage_index.php`는 공개 엔드포인트지만 남의 사이트 데이터.
**1회 스냅샷으로 정적 내장**, 반복 호출 금지, 출처 표기.

## 11. 길드 100명이 값을 하는 지점

혼자서는 못 하고 100명이 있어야 되는 것들. **백엔드가 필요한 진짜 이유** (스크린샷 파싱은 부차적).

1. **모든 스킬 레벨 파급효과** — 잠재는 되돌릴 수 없어 본인 측정 불가. 이미 가진 사람의 before/after만이 유일한 길
2. **직업별 버프 효과 테이블** — 14직업, 각 1명씩만 ON/OFF 스탯창 2장
3. **직업별 스킬 DB** — 14직업 × 1명
4. **미지 계수 역산** — 실측 제출이 쌓이면 회귀로 정확도 상승

→ **쓸수록 정확해지는 계산기**. Railway 백엔드에 테이블 몇 개면 된다.

## 13. 배포

**웹으로 만들고 앱은 WebView로 감싼다.**
- 계산기는 로직이 계속 바뀐다(캘리브레이션·밸패·공식 변경). 앱 배포 사이클에 묶으면 고통
- 웹은 `git push` 한 번 → 즉시 반영, 앱 재배포 없이 계속 개선
- 유지보수 지점 한 곳
- 앱 레포는 원격이 없어 데스크탑에서 push해야 하는 제약도 우회

### 구현 순서
1. 계산 엔진 + 랭킹표 (JS, 손입력 21칸) — 실제 스탯으로 즉시 검증 가능
2. 직업 14종 · 유물 체크박스 · 콘텐츠 탭
3. `item_compare.py`에서 `verdict` 제거 → 파싱 전용 + Haiku
4. 직업별 버프/스킬 프리셋 테이블 (백엔드)
5. 웹 배포 → 앱 WebView

1번만 나와도 바로 쓸 수 있고, 랭킹표가 실제 체감과 맞는지 검증도 거기서 된다.
